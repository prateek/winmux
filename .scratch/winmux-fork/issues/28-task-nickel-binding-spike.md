# Task: Nickel binding spike

Type: task
Status: resolved

## Question

Can WinMux call Nickel functions from Swift through a thin Rust binding over `nickel-lang-core`, and what does it cost? [Prototype: config and scripting language](27-prototype-config-language.md) chose Nickel with our own binding instead of the shipped C API. Settle these with a throwaway Rust crate plus a Swift caller (AFK):

1. Can `nickel-lang-core` keep an evaluated closure from a loaded config and apply it to a new value built from Swift data, without re-parsing? Which internal API does that, and how stable has it been across the last few releases?
2. What does one call cost? Measure a Filter over about 50 synthetic windows per Lens open (per-window calls vs one call over the whole array) one `arrive` call, and one `place` call per selection change while Summon's modifier is held (the landing-spot hint of [Prototype: grid Presentation look and behaviour](08-prototype-grid-presentation.md)), cold and warm.
3. The UniFFI or swift-bridge shape: how `Window`, `App`, the Filter context and Columns are marshalled in, and how returned records and Nickel diagnostics come back.
4. Does Nickel's documented `.toml` import work, which would help `winmux config convert`?
5. Build from source on macOS (the 1.18 release artifacts link libiconv from `/nix/store`): toolchain, binary size added to WinMux, and a version-pin and upgrade policy.

## Answer

Yes, it works and it's fast, but `nickel-lang-core` leaks memory on nearly every call, so the evaluator can't live inside the WinMux process for weeks. Measured 2026-09-30 on the Mac mini M4 (`Mac16,10`) stand-in, `nickel-lang-core` 0.19.0, Rust 1.96, Swift 6.3, with the reference config from the config-language prototype plus `arrive`. Spike: [prototypes/28-nickel-spike/](../prototypes/28-nickel-spike/) (`bench.txt` and `swift-bench.txt` hold the raw numbers).

1. **Holding and calling functions: yes, without re-parsing.** Keep one `VmContext` for the loaded config, evaluate it with `VirtualMachine::eval_closure`, walk records to the function, then evaluate `Term::app(f, arg)` with `eval_full_closure` in the function's own environment. This is what `nickel-lang` 2.2's `Context::eval_expr_shallow` does internally. The binding must hold a `Closure` (value plus environment), not a bare `NickelValue`. A function wrapped by a function contract (`Window -> Dyn -> Bool`) refers to stdlib contract internals through its environment, and holding only the value fails with ``unbound identifier `Codomain` ``. The same goes for passing a held function back into another Nickel function as an argument: it has to be closurized into a thunk first. The spike skipped that, so its one-call-over-array variant takes the Filter's name. WinMux doesn't need that path, since it looks up `lenses.<name>.filter` and calls it per window, so the `filter = filters.same_app` shape stands. Stability: `VmContext`, `prepare_eval`, `eval_closure`, `eval_full_closure`, `Closure { value, env }`, `Term::app` and `NickelValue` have the same signatures in 0.16.1, 0.17, 0.18 and 0.19 (Dec 2025 to Sep 2026). 0.15 used `RichTerm` and a `Closure { body }`, so the value representation changed once, a year ago. Minor releases come about every three months, move in lockstep with the CLI, and are allowed to break (0.x).
2. **Cost is small.** Load (parse, typecheck, stdlib, WHNF) takes 5 ms in-process and 13 ms from Swift. A 50-window Lens open costs 0.8 ms for `same_app` and 2.0 ms for `here` (which calls `floaters` and `std.array.elem`). One call over the whole array is only 15–25% cheaper than 50 per-window calls, so per-window calls are fine. `place` costs 0.16 ms and `arrive` 0.07 ms. First calls are within 25% of warm ones, since there's no JIT or cache to warm. From Swift, including `JSONEncoder` (0.18 ms per Lens request), a Lens open takes 2.4 ms and `place` 0.21 ms. So Summon's landing-spot hint can call `place` on every selection change. The `W.Config` function contracts cost more than the Filter bodies: `same_app` runs 7× faster without them (2.2 µs vs 15.6 µs per window), and `place` 2×.
3. **Marshalling.** Host data goes straight to `NickelValue` (`record_posless`, `array_posless`, `enum_tag_posless`), with no Nickel source text or new `Program`: 50 windows plus the Filter context take 45–130 µs. Enum fields (`class`, `profile`, Column refs) must become enum tags, so the binding needs typed input that knows which fields are enums. JSON alone loses that; the spike cheats with a leading `'`. Results are walked back to JSON, with tags as `'tag`, after `eval_full_closure`. `NickelValue` is `Rc`-based and not `Send`, so all Nickel state stays on one thread. Diagnostics come from `report_as_str` over the context's `Files` as the same codespan text the CLI prints, `Did you mean `bundleId`?` and contract blame on `'focussed` included. A failed call doesn't poison the engine. The `Window` contract on a Filter's argument didn't catch host data with a missing `title` before the body ran, since contracts are lazy, so the typed marshalling has to be the guard for host data. The spike proves the path with a C ABI (JSON in, JSON out) linked into a `swiftc` caller rather than UniFFI or swift-bridge. Because of point 6, the real boundary is probably a process boundary, which makes that choice moot.
4. **TOML import works.** `import "legacy.toml"` gives a record that merges like any other (`{ gaps = 8, workspace.comms.columns = 3 }` came through). So `winmux config convert` can read the old file through Nickel itself; printing the result as Nickel source is still its own code.
5. **Build.** `default-features = false` drops the REPL, formatter, doc and markdown dependencies: 123 crates, 54 s for a cold release build, Rust ≥ 1.89 (edition 2024). It links the system `/usr/lib/libiconv.2.dylib`, so the `/nix/store` problem of the release binaries doesn't arise. Size: the stripped Rust helper binary is 15.4 MB; linked into the Swift caller it adds 31 MB stripped. The gap is most likely unused code in the staticlib that the Swift link doesn't strip; no size tuning was tried. Policy: pin `=0.19.0`, upgrade on purpose with each CLI release, and gate the upgrade on the spike's calls and the smoke run.
6. **The blocker: memory leaks.** RSS grows with every call that touches the stdlib or builds closures, and dropping the engine frees nothing: 5–7 KB per `std.array.elem` or `std.array.any` call, about 160 KB per 50-window Lens open with `here`, about 6 KB per `arrive`, and 37 KB per `place` (10 KB of it without contracts). A plain field comparison or a record literal leaks nothing. It happens inside a single evaluation too, so it's the evaluator, not the binding. Upstream knows: [nickel-lang/nickel#1908](https://github.com/nickel-lang/nickel/issues/1908), "Memory leak with long-running nickel process", open since May 2024. Recursive records (and the stdlib is one) create `Rc` cycles through thunk environments. It's "not a problem for one-shot eval… but it might be a blocker for people trying to embed nickel", and the one maintainer comment (May 2024) floats swapping `Rc` for a cycle-collecting pointer. No fix PR exists. Nickel's own language server hit the same leak and fixed it by running each background eval in a separate process ([nickel-lang/nickel#1869](https://github.com/nickel-lang/nickel/pull/1869), merged). At a few hundred Lens opens a day that's tens to hundreds of MB a day, unbounded.
7. **A helper process costs nothing measurable.** The same binary serving JSON lines over a pipe gives the same timings from Swift: 2.2 ms per Lens open, 0.20 ms per `place`. A warm spawn plus load plus first call takes 7.6 ms; the first exec of a new unsigned binary took 412 ms once. So WinMux can run the evaluator in a helper and recycle it on an RSS threshold or on config reload, off the hot path. Where the evaluator runs is now its own decision: [Grilling: where the Nickel evaluator runs](31-grilling-nickel-evaluator-process.md).
