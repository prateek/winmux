# Grilling: where the Nickel evaluator runs

Type: grilling
Status: resolved

## Question

`nickel-lang-core` leaks memory on almost every call that touches the stdlib (upstream issue nickel-lang/nickel#1908, open since 2024), about 160 KB per 50-window Lens open, and dropping the engine frees nothing ([Task: Nickel binding spike](28-task-nickel-binding-spike.md)). Where should WinMux evaluate Filters and Policy hooks? The main candidate is a supervised helper process (a small Rust binary shipped inside the app), recycled on an RSS threshold or config reload. It adds no measurable call cost over a pipe, and a warm respawn takes 7.6 ms. Nickel's own language server made the same choice for the same leak (nickel-lang/nickel#1869). The alternatives are in-process with periodic WinMux restarts, patching Nickel upstream (cycle collection), or revisiting the language choice. If it's the helper, settle the transport (pipe or XPC), the request shape (one batched request per Lens open; typed enum fields), what WinMux does while the helper restarts or after it crashes (block, time out, fall back to the last result or to "match everything"), who runs the load-time smoke run, and how reload swaps helpers atomically.

## Answer

Resolved 2026-09-30 with Prateek. Nickel runs in a supervised helper process, and WinMux never links it. No `CONTEXT.md` change, since the helper is implementation; the reasoning is recorded in [ADR 0001](../../../docs/adr/0001-nickel-helper-process.md).

- **Where.** A small Rust binary shipped in the app, recycled to throw the leak away. In-process with self-restarts, patching Nickel (cycle collection) and reopening the language choice were all rejected. A patch stays a possible upstream contribution, off the route.
- **The helper owns the whole config.** At load it evaluates the file, returns the static part (gaps, bindings, Width presets, Lens records minus their functions) as plain JSON, and keeps the functions for later calls: Filters, `arrive`, `place`, `move-boundary`, and Tab provider `transform` and `focus`. Static data and functions always come from the same evaluation.
- **Transport.** WinMux spawns the helper and talks JSON lines over its stdin and stdout, with a request id on every message. WinMux is the parent and supervises it. XPC was rejected: it needs a bundled, separately signed service and doesn't fit `swift run` builds or the CLI.
- **Typed marshalling.** WinMux sends plain JSON strings. The helper holds a typed Rust struct per host record (`Window`, `App`, Filter context, Column) that knows which fields are enum tags and rejects a record with a missing field before any Nickel runs. Nickel's contracts are lazy and missed that in the spike. The structs are versioned with the Filter contract and ship in the same app.
- **Requests.** One batched request per Lens open (Filter context plus all windows, answered with a match bit per window). One request per `arrive`, `place` or `move-boundary` call, and per provider `transform` or `focus`. Sort and Search ranking stay in Swift unless a key is a Nickel function. `lens --filter '<expr>'` and Search's `=` prefix go to the same helper as an `eval-filter` request, evaluated in the loaded config's environment and compiled per request, not cached.
- **One helper, strict FIFO.** Nickel state is single-threaded. A Lens open takes about 2 ms, so a queued `place` waits at most that long; a pool would hold several copies of the config for no gain.
- **Recycling.** On every config reload, and when the helper's RSS passes 256 MB (it reports RSS in each reply). The replacement is spawned, loads and passes the smoke run in the background, then WinMux swaps it in between requests and closes the old one's stdin. 256 MB is a knob: it's about 1,600 Lens opens at 160 KB each, fewer in a session heavy on Summon, since `place` leaks 37 KB per call and runs on every selection change.
- **Timeouts and fallbacks.** A Filter gets 100 ms, then the Lens shows every window with a banner saying the Filter failed (a stale result could hide a new window). Hooks get 50 ms, then the built-in behaviour as if no hook were configured: the Overflow policy default and the plain boundary move. A failed provider `focus` shows a notification. A timed-out request means the helper is hung: WinMux kills it (SIGKILL) and respawns, and request ids keep a late reply from being misrouted.
- **Crashes.** A crashed helper restarts at once with backoff (1, 2, 4 s, capped at 30 s). After 3 crashes in a minute a circuit breaker stops respawning; WinMux keeps the static config it has and runs with the fallbacks above. `reload-config` resets the breaker, and so will a config file change once hot reload exists. A notification fires when the breaker trips.
- **Startup.** WinMux waits for the first load before managing windows, with a 2 s timeout (a warm load is about 8 ms; the first exec of a freshly signed binary took about 400 ms once). On failure or timeout it runs on built-in defaults, the same as with no config file, and shows the diagnostic. No last-good config is cached on disk.
- **Reload.** The fresh helper loads the file, checks contracts and runs the smoke run itself. On success it returns the static JSON plus the resolved list of imported files; WinMux applies the data and swaps helpers atomically, with in-flight requests finishing on the old one. On failure the old helper and config stay and `reload-config` exits non-zero with the diagnostic. An open Lens keeps its already-filtered entries until it closes.
- **One binary, two modes.** `serve` is the JSON-lines loop. `check <file>` (load plus smoke run) and `convert <file>` (TOML to Nickel) are one-shot, and the `winmux` CLI execs them directly, so they work with the server down.
- **Name, place, build.** `winmux-nickel` at `WinMux.app/Contents/Helpers/winmux-nickel`, built with `cargo build --release` from a `nickel-helper/` crate in this repo, `nickel-lang-core` pinned `=0.19.0`. `script/dogfood-release` signs it with the app's identity; it needs no TCC grants. Dev builds find it through `WINMUX_NICKEL_HELPER`, falling back to the path next to the executable. Rust becomes a build dependency.
- **CLI** (feeds [Grilling: CLI surface for the fork's features](20-grilling-cli-surface.md)): `winmux config status` prints JSON with the helper's state (`ready`, `restarting`, `failed`), pid, RSS, recycle count, last error and loaded config path. `winmux config check <file>` and `winmux config convert` run the helper's one-shot modes.
