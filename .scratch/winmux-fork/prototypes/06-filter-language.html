The question

Should a Filter in the WinMux fork be an expression string in winmux.toml (a small language WinMux parses and checks itself), or a JavaScript predicate run by JavaScriptCore? A Filter decides which windows a Picker shows, and it can read the Filter context: the focused window, the window under the mouse, the previous window, the current workspace, project and monitor, and the Display profile.

  • Names. The expression language reuses the kebab-case names winmux list-windows --format already has (app-bundle-id, monitor-name) and adds the new ones the research asked for (window-class, app-activation-policy, window-subrole, window-level, window-has-close-button, window-is-registered, monitor-uuid, monitor-is-built-in). JavaScript wants camelCase and nesting (w.app.bundleId, w.monitor.uuid), so the JS option means a second spelling of every attribute.
  • What the JS column is. It runs in this browser's JavaScript engine, standing in for JavaScriptCore. It shows how filters read and how their errors look, not JavaScriptCore's speed or sandboxing. Those are still fog on the map.
  • What "today" means. Each card also says whether WinMux's existing [[on-window-detected]] if matcher (app-id, app-name-regex-substring, window-title-regex-substring, workspace, during-winmux-startup) could express it.
  • The pretend desktop has 15 windows over four workspaces in two projects, including an Accessory app (Ghost Pepper) whose close-button-less window WinMux classifies as a popup, a regular app's popup (Arc autofill), and a CleanShot pin WinMux has never registered. Bundle ids and UUIDs are illustrative.
